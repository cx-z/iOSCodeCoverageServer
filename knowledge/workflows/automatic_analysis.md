# Automatic analysis workflow

1. **Entry:** valid Run, pending-Run promotion, or admin/operator retry.
2. **Call chain:** route -> `AnalysisScheduler.request_analysis` -> `AnalysisStateStore` generation -> worker claim -> process-isolated `CycleAnalysisOrchestrator.analyze`.
3. **Persistence:** generation and small latest-success references in SQLite; immutable stage outputs under root `analysis/`.
4. **Background behavior:** one global scheduler worker; new generations arriving during a run coalesce into one subsequent latest snapshot. Each production attempt owns a separate process group containing the orchestrator and its LLVM/Git commands. That execution chain inherits the server's runtime-lock lease, so runtime ownership survives an unexpected parent-service exit until the last analysis process exits. Coordinated cleanup may pause new claims only after the active analysis completes; queued generations remain durable and resume afterward.
5. **Success:** state points to a completion-validated orchestration and Cycle result. The report API reads that latest success.
6. **Failure:** stable stage/code/message are saved, the Run and old latest success remain, and there is no unbounded retry. If the analysis leader exits before a child command, the remaining process group is terminated and confirmed empty before scheduler-idle publication. A termination failure is fail-closed: the durable generation remains `running`, the scheduler retains runtime execution ownership, and cleanup plus subsequent analysis stay blocked. Only after the group is proven absent may the failure be persisted and the scheduler become idle; failure-persistence exceptions therefore cannot authorize cleanup while a process remains. Coordinated SIGTERM shutdown uses the same bounded group termination; SIGKILL or a crash cannot release the inherited runtime lease while an analysis process remains. A cancelled generation remains recoverable instead of being recorded as an analysis failure.

The orchestrator snapshots all Build/Run rows, selects current by Cycle `head_sha`, resolves the Cycle project's registered repository, independently analyzes each Build, creates current diff, and accumulates source regions. After cleanup, incorporated Runs are accepted only through completion-verified retained Build evidence; a later same-Build Run merges with that Build's retained profile baseline, while different Builds remain independent. Tests: `tests/server/test_automatic_analysis.py`, `tests/analysis/test_orchestrator.py`, `tests/lifecycle/test_runtime_cleanup.py`, `tests/lifecycle/test_runtime_cleanup_manager.py`. Guides: `docs/automatic_analysis.md`, `docs/runtime_data_lifecycle.md`.

The current diff and every historical Build normalize LLVM paths against that Build's fixed Git tree. A whole export with code regions but no mapped project region fails the generation at `current_diff` or `cumulative` with `coverage_path_mapping_failed`; it cannot publish a false all-unmeasurable report. An admin/operator retry after deploying the mapping fix reuses immutable Build/Run inputs and recomputes the versioned orchestration, diff, and cumulative results. The orchestration identity must change too: it checks for a complete prior result before calling either downstream analyzer. The last completed report remains the latest success during failure and retry.

New Debug packages use repository-relative coverage paths: exact names are checked against each Build's fixed Git tree without selecting a checkout root, and regions/segments pass fixed-blob coordinate checks. Relative and legacy absolute exports can accumulate in one Cycle through conservative cross-Build region inheritance; profiles from different Builds remain separate. Local absolute paths retain symlink resolution. Differently named legacy absolute-path checkouts require the project's startup-fixed `compiler_repository_names` allowlist (default: registered repository basename). One unique allowlisted root is selected against fixed Git paths, then reused by directory-boundary prefix stripping. Exceptional paths are checked for a second valid root; a one-time Git-path ambiguity index prevents prefix reuse from hiding a later nested valid split. Unregistered names are never automatically inferred. Mapped regions/segments pass the same fixed-blob coordinate checks. External/generated paths without a Git match stay unmapped. A successfully mapped zero-count changed region remains `uncovered`; mapping success never creates positive hit evidence. The directory-name policy participates in orchestration, diff, and cumulative identities so a configuration change cannot bypass revalidation through a cached success.

If formal selection fails with no current Build or no analyzable current-Build Runs, the same background attempt independently validates/analyzes ready Builds that do have valid Runs. Each successful same-Build result gets an atomic, fsynced completion-bound reference through `storage/build_evidence.py`; a local Build failure does not block other independent results. Formal selection still fails with its original code, keeps the previous latest-success pointer and report denominator, and does not fabricate a current-Build report. MR projection can read newly published A evidence despite a missing or untested B. The resolver remains read-only. Tests: `tests/analysis/test_independent_mr_evidence.py` exercises the real scheduler, SQLite, orchestration, atomic evidence store and fixed-Git consumer with a controlled LLVM boundary.
