# Coverage report workflow

1. **Entry:** `/login/` is the account entry, `/cycles/` is the Session-gated workbench, and `/cycles/<cycle_id>` plus report JSON endpoints remain the report entry. When `anonymous_read` is enabled, the resolver, report, and report-file endpoints used by the browser extension are served without a credential; otherwise they require any valid platform principal. The browser UI uses HttpOnly Session and never stores machine Tokens.
2. **Call chain:** page route -> web shell; browser -> analysis/report API -> `CoverageReportStore`.
3. **Persistence:** none. The store derives fixed result directories from latest-success identities and validates completion/file SHA before projection.
4. **Background trigger:** none; two-second page refresh is read-only.
5. **Success:** summary, safe file IDs, changed-line states, source text already stored in analysis output, and current/historical evidence labels.
6. **Failure:** missing/tampered results are rejected; queued/running/failed states may continue showing the prior latest success.

An export containing compiler code regions but no project mapping fails analysis before publication. Genuine unmeasured compiler lines retain `not_measurable` semantics. Report and report-file APIs validate immutable latest-success output without comparing it with live MR refs. The Cycle page always displays that report's stored source, decisions and formal denominator.

The read-only MR resolver supports two explicit protocols. Schema 1 preserves the three-Build-ref equality gate and returns `stale_diff` on mismatch. Schema 2 requires the page-selected numeric `page_version` (GitLab diff ID), verifies it through the registered MR's latest diff-version metadata and compares all three refs with the live MR. It then returns a separate presentation bound to Cycle, target base/start/head, page version, report generation, current Build, orchestration and input-set hashes. A page that still calls its old version “latest” is rejected. The resolver never creates a Cycle, advances its head, schedules LLVM, or modifies a report.

For an exact match without additional unincorporated independent evidence, schema 2 uses the original completion-verified report projection. Otherwise `analysis/mr_presentation.py` reads the current fixed Git diff and independently normalized, completion-bound single-Build exports referenced by the successful orchestration plus independently published Build references from `analysis/build-evidence/<cycle>/<build>.json`. The latter are published by the background orchestrator even when no analyzable current Build exists, and do not advance formal latest success. References already incorporated into the formal Run set are ignored. A Build with no successful result supplies no evidence. Each Build is mapped directly to current code through exact paths/one-to-one rename, Git unchanged hunks, exact line content and an ambiguity veto (`mapping/mr_lines.py`). No whole-region invalidation is used for this display-only path. A full same-Build line hit or an already complete, completion-verified published line decision (including mixed historical region evidence) wins over other missing/unhit evidence. Published decisions are mapped from their own fixed Build source snapshot, never relabeled as the current MR source. Definite new/modified lines are red; ambiguous/unreadable parts are unknown. Historical gray classifications apply only to mapped unchanged lines. Different profiles remain independent.

MR presentations are immutable derived in-memory snapshots, never formal reports. Logical inputs include independent Build reference identities even when the formal report generation is unchanged. The resolver owns an eight-entry cache protected by a lock, with at most two cold projections at a time; disk/network/Git work runs outside the cache lock. A per-input Future gives one computation owner; waiters do not hold the cache lock. Issued IDs also hash the actual complete snapshot contents, so a summary and all details under an ID remain immutable. Transient data failures are retried after 15 seconds; changed recovered contents receive a new ID while the old ID retains its original details until eviction. Genuine immutable mapping ambiguities do not trigger these retries. File reads require the issued presentation ID, page version and exact server file ID in the same registered project/MR. Eviction/restart returns `presentation_expired` and requires re-resolution. Counts cover the complete current MR new side, not loaded DOM rows. Mapped projections have no coverage percentage or compiled denominator, including matching refs with additional independent evidence not yet incorporated into the formal report. Background pending/failed status remains visible while valid evidence is annotatable. Source Build, commit, input/export identities accompany positive evidence; the resolver report reference retains the published report time.

The extension verifies the active version link before/after requests, and verifies each actual row's structured comment `data-position` (three refs, exact new path, new line) before applying schema-2 markers. Unverified rows receive no marker. Route, page version, presentation and controller/file revision invalidate late work. Its viewport scheduler remains limited to four file requests with incremental file discovery and 200-marker batches. Metadata polls detect report/MR updates even if generation is unchanged.

The Web layer never receives arbitrary filesystem paths and browser text uses safe DOM projection. Tests: `tests/web/test_report_ui.py`, `tests/server/test_gitlab_coverage_resolver.py`. Guide: `docs/coverage_report_ui.md`.

Large-file mapping first proves complete earliest/latest subsequence embeddings or uses a bounded edit-distance band; repeated text alone cannot invalidate a uniquely ordered unchanged block. If both alignment budgets are exhausted, no unproven Git candidate inherits coverage: common rows remain unknown, while definite novel rows remain uncovered. Text uniqueness alone does not prove forced identity across optimal alignments. Rename ambiguity is checked only against actual competing removed/added identities using fixed, literal-path Git comparisons, so an unrelated added file does not invalidate a rename.
