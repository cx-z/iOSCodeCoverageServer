# Coverage report workflow

Both mapped and strict schema-2 MR presentations exclude proven non-executable changes independently of matching Build availability. `mapping/file_classification.py` owns the explicit configuration/resource data policy: plist, JSON, xcconfig, entitlements/privacy, localization, Xcode/dependency metadata, UI/data-model files and common document/image/font/audio/video formats. Binary diffs already have no changed source lines. A resource folder name alone never excludes executable Swift, JavaScript, C++ or Metal source.

`mapping/source_comments.py` scans complete fixed Git blobs and preserves literals as opaque tokens. `mapping/source_non_executable.py` classifies pure comments, whitespace, standalone structural delimiters, imports/compiler directives and proven type/declaration syntax, including multiline signatures and Objective-C declarations. Runtime initializers, default argument expressions, inline bodies, switch branches, immediate closure calls, runtime-sized arrays (including function parameter bounds), C++ object construction, unary cast expressions and mixed declaration/statement lines retain their evidence-based decisions. Objective-C method proof requires a declaration container outside a method/function body; Swift accessor ownership excludes initializer closures and distinguishes explicit accessor lists from implicit getter execution bodies; even a pure local declaration starts implicit getter ownership. Declaration continuation tracks generic return-type delimiters through the complete type boundary and permits a separate accessor-opening brace without transferring ownership to initializer closures. C parameter array bounds are inspected as complete multiline expressions before excluding declaration fragments. Declaration continuation ends at its own signature/body boundary. C line splicing is lexed logically and projected back to original physical row numbers; directive continuation state updates even on blank/comment rows, and the same complete directive-row set is excluded from array-bound scanning. Strict presentation copies apply the same file/line policy and recompute summary/file/detail counts; formal stored reports remain immutable. Unreadable current source remains unknown on the mapped path; a strict snapshot retains its verified decision and requests a retry when fixed source cannot be read.

1. **Entry:** `/login/` is the account entry, `/cycles/` is the Session-gated workbench, and `/cycles/<cycle_id>` plus report JSON endpoints remain the report entry. When `anonymous_read` is enabled, the resolver, report, and report-file endpoints used by the browser extension are served without a credential; otherwise they require any valid platform principal. The browser UI uses HttpOnly Session and never stores machine Tokens.
2. **Call chain:** page route -> web shell; Cycle browser -> `GET /api/v1/cycles/<id>/mr-presentation` -> `MergeRequestCoverageResolver.resolve_cycle_presentation` -> existing schema-2 mapping/cache. Formal report APIs still delegate to `CoverageReportStore`.
3. **Persistence:** none. The store derives fixed result directories from latest-success identities and validates completion/file SHA before projection.
4. **Background trigger:** none; two-second page refresh is read-only.
5. **Success:** latest MR summary and fixed-head changed-line source from an immutable presentation; details require the same Cycle, presentation ID, page version and file ID. Non-MR Cycles retain the formal report view. Formal Build identity, percentage and publication time are labeled separately.
6. **Failure:** missing/tampered results are rejected. A valid MR projection may still use prior successful evidence while analysis is pending/failed. An unverified version, closed/merged MR or GitLab/network failure makes the browser independently read the formal `/report` API. A valid formal report remains browsable through `/report/files`, explicitly labeled as a formal Build diff rather than latest MR. The notice states why projection is unavailable; later successful polling restores the current MR view. Missing/corrupt formal results remain errors, and authentication failures never trigger fallback.

The extension POST schema-2 boundary keeps non-strict summary/file descriptors at `measurable:0` with a null percentage, including file details. The Cycle GET summary/details retain their computed ratio. Both use the same immutable presentation and line evidence; output conversion changes only request-owned copies.

The Cycle-only entrypoint also supports `status: diff_only` when an open MR has no successful formal report. It still compares the latest diff version's complete refs with the live MR, then runs the existing fixed-Git projector with no Build evidence or published decisions. It reuses the bounded immutable presentation cache and bound detail protocol, with a separate source-only input identity. Readable explicitly non-instrumented paths remain `not_measurable`; other readable lines have no positive evidence and remain `uncovered`; source failures remain unknown. No compiled denominator, percentage, Build or formal report is fabricated. The response keeps `report: null` and reports the existing Cycle `build_count` so the page distinguishes no package from an existing package awaiting a successful report. Pending/failed analysis remains visible. Extension resolver schemas retain their successful-report gate. A later first successful report replaces this source-only view through normal presentation invalidation.

Report `updated_at` comes from the selected successful orchestration’s completion-verified `summary.json` → `completed_at`, not the scheduler’s mutable latest-attempt `completed_at`. Queued, running and failed attempts preserve the prior report’s timestamp and contents; new successful publication advances the report together. This applies to report/file APIs and both MR resolver schemas.

An export containing compiler code regions but no project mapping fails analysis before publication. Genuine unmeasured compiler lines retain `not_measurable` semantics. Report and report-file APIs validate immutable latest-success output without comparing it with live MR refs. The Cycle page instead uses the latest registered MR diff projection, without changing these formal endpoints or their denominator. The server reads the latest diff ID and compares its complete refs with the live MR before issuing the shared immutable presentation. Source text in mapped details comes from that fixed target head; the extension still verifies its own page-selected version and DOM row refs. Polling keys off presentation identity, so MR or independent-evidence changes update the page even with an unchanged formal generation. Late file responses cannot overwrite a newer selection or snapshot; expired snapshots trigger resolution again and retry the requested file once, even when a restart recreates the same presentation ID. Concurrent recovery joins the active refresh promise; a newer click supersedes that recovery. Admin analysis request/start/completion timestamps remain separate from the immutable report publication time.

The read-only MR resolver supports two explicit protocols. Schema 1 preserves the three-Build-ref equality gate and returns `stale_diff` on mismatch. Schema 2 requires the page-selected numeric `page_version` (GitLab diff ID), verifies it through the registered MR's latest diff-version metadata and compares all three refs with the live MR. It then returns a separate presentation bound to Cycle, target base/start/head, page version, report generation, current Build, orchestration and input-set hashes. A page that still calls its old version “latest” is rejected. The resolver never creates a Cycle, advances its head, schedules LLVM, or modifies a report.

For an exact match without additional unincorporated independent evidence, schema 2 uses a copy of the completion-verified report projection with proven non-executable file/line changes excluded from its display denominator. Otherwise `analysis/mr_presentation.py` reads the current fixed Git diff and independently normalized, completion-bound single-Build exports referenced by the successful orchestration plus independently published Build references from `analysis/build-evidence/<cycle>/<build>.json`. The latter are published by the background orchestrator even when no analyzable current Build exists, and do not advance formal latest success. References already incorporated into the formal Run set are ignored. A Build with no successful result supplies no evidence. Each Build is mapped directly to current code through exact paths/one-to-one rename, Git unchanged hunks, exact line content and an ambiguity veto (`mapping/mr_lines.py`). No whole-region invalidation is used for this display-only path. A full same-Build line hit or an already complete, completion-verified published line decision (including mixed historical region evidence) wins over other missing/unhit evidence. Published decisions are mapped from their own fixed Build source snapshot, never relabeled as the current MR source. Definite new/modified lines are red; ambiguous/unreadable parts are unknown. Historical gray classifications apply only to mapped unchanged lines. Different profiles remain independent.

MR presentations are immutable derived in-memory snapshots, never formal reports. Logical inputs include independent Build reference identities even when the formal report generation is unchanged. The resolver owns an eight-entry cache protected by a lock, with at most two cold projections at a time; disk/network/Git work runs outside the cache lock. A per-input Future gives one computation owner; waiters do not hold the cache lock. Issued IDs also hash the actual complete snapshot contents, so a summary and all details under an ID remain immutable. Transient data failures are retried after 15 seconds; changed recovered contents receive a new ID while the old ID retains its original details until eviction. Genuine immutable mapping ambiguities do not trigger these retries. File reads require the issued presentation ID, page version and exact server file ID in the same registered project/MR. Eviction/restart returns `presentation_expired` and requires re-resolution. Counts cover the complete current MR new side, not loaded DOM rows. Mapped projections with a successful formal report compute `measurable = covered + uncovered` and `changed_line_coverage_percent = covered / measurable * 100`, for both the whole current MR and each file. `not_measurable`, `unknown` and deleted lines are excluded; a zero denominator returns null. This is a display-state ratio, not the old Build compiled denominator, and it remains available after MR commits change or independent evidence arrives. The source-only `diff_only` view keeps `measurable: 0` and a null percentage until a first successful report exists. Background pending/failed status remains visible while valid evidence is annotatable. Source Build, commit, input/export identities accompany positive evidence; the resolver report reference retains the published report time.

The extension verifies the active version link before/after requests, and verifies each actual row's structured comment `data-position` (three refs, exact new path, new line) before applying schema-2 markers. Unverified rows receive no marker. Route, page version, presentation and controller/file revision invalidate late work. Its viewport scheduler remains limited to four file requests with incremental file discovery and 200-marker batches. Metadata polls detect report/MR updates even if generation is unchanged.

The Web layer never receives arbitrary filesystem paths and browser text uses safe DOM projection. Tests: `tests/web/test_report_ui.py`, `tests/server/test_gitlab_coverage_resolver.py`. Guide: `docs/coverage_report_ui.md`.

`storage/cumulative_lines.py` reads two cumulative-line disk formats. Legacy schema 1 contains inline `lines[].regions` (older minimal documents without a schema field are also treated as inline). Schema 2 contains `lines[].region_ids`, zero-based integer indices into the same completed directory's `mapping-evidence.json` → `region_mappings` list. That existing, deterministically sorted table stores each full region decision and its historical attempts once; no second evidence table is embedded in the line document. New-format indices must be integers (not booleans), in bounds and refer to the exact line's repository path; inline/reference mixtures and unknown schemas are rejected. Decoding restores the previous in-memory line shape using read-local shared region dictionaries. Public report/file schema 1 and MR resolver schemas remain unchanged, as do all counts, coverage sources and stored decisions. No old result is rewritten or migrated in place.

Report JSON reads remain size-bounded: ordinary metadata and independent LLVM exports use a 128 MiB limit. `cumulative-line-coverage.json` retains its separate 512 MiB limit for large legacy inline reports; the required schema-2 `mapping-evidence.json` has a dedicated budget of the same size so extracting inline decisions into a shared table does not subject them to the smaller metadata limit. Each file is bounded independently. Summary, file details and strict MR snapshots share the decoder after completion output-set, size and SHA-256 verification, including the referenced mapping table. New analysis versions create fresh immutable results; ordinary reads continue serving old reports without requiring reanalysis. The real-publisher capacity regression is covered in `tests/analysis/test_cycle_coverage.py`; table-boundary and ordinary-metadata limits are covered in `tests/web/test_report_ui.py`.

Large-file mapping first proves complete earliest/latest subsequence embeddings or uses a bounded edit-distance band; repeated text alone cannot invalidate a uniquely ordered unchanged block. If both alignment budgets are exhausted, no unproven Git candidate inherits coverage: common rows remain unknown, while definite novel rows remain uncovered. Text uniqueness alone does not prove forced identity across optimal alignments. Rename ambiguity is checked only against actual competing removed/added identities using fixed, literal-path Git comparisons, so an unrelated added file does not invalidate a rename.
